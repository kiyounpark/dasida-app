## 한 줄

**홈은 세 화면을 다 갖췄는데, 학생은 두 번째에서 멈춘다.**

```
사진 0장   → 소개 화면 (web-proto 문구)      ①  된다
사진 1장~  → "아직 복습할 게 없어요"          ②  된다 ← 여기서 멈춘다
복습 있음  → 복습 리스트                      ③  만들어뒀는데 아무도 못 본다
```

②에서 ③으로 가는 다리가 **E칸**이고, 그게 아직 없다.
**고칠 자리는 홈이 아니다** — 홈은 ③까지 다 그려놨고 테스트도 통과한다.
없는 건 노트를 복습 과제로 바꿔 주는 쪽이다.

## 목표 (🔒 2026.09.15 · 결정 B)

다시다는 **복습 앱**이다. 홈은 "오늘 복습할 것"이고, **복습 재료가 빌 때마다**(최초 1회가 아니라) 사진 등록을 요구한다. 졸업은 없다 — 재료가 떨어지면 다시 채우는 순환이다.

### 🔧 정정 — "E는 C 뒤다"는 절반만 맞다 (2026.09.15)

이 파일은 오래 **"E는 C가 먼저 풀려야 한다"**고 적어 왔다. F 작업 중 노트 구조를
열어보니 **절반만 맞는 말이었다.**

`features/photo/types.ts`의 `PhotoNote`에 이게 이미 들어 있다:

```
weaknessIds: WeaknessId[]             통역표가 찾은 약점들
primaryWeaknessId: WeaknessId | null  하나로 좁혀진 것
```

복습 과제를 만드는 데 필요한 건 **약점 id 하나**인데, 그게 이미 노트에 붙어 있다.

- 노트 **전부**를 과제로 만들려면 → C가 필요하다 (186칸 중 55칸만 참이니까)
- **약점이 붙은 노트만** 만들려면 → **C 없이 지금 된다.** 대략 3분의 1

**그래서 C를 기다릴 이유가 없다.** C는 "과제가 얼마나 많이 생기냐"를 정할 뿐이고,
E는 "과제가 생기냐 마냐"를 정한다. 0건에서 벗어나는 건 E다.

C는 기윤의 수학 판단이 계속 필요한 제일 느린 칸이다. 이 정정이 없으면
다음 방이 C부터 붙잡고 한참 돌아간다.

**단, E를 열기 전에 확인할 것:** `review-task-store` 쪽을 복습날짜(D) 방이
보고 있다. 겹치면 지금 열면 안 된다. (F방은 이 확인을 안 했다 — 남의 방이라 안 열었다)

---

**C · D는 서로 독립이라 같이 가도 된다.** 파일이 안 겹친다 (단 D는 읽기 전용일 때).

**순서 제안: E → D → C.**
E가 있어야 과제가 생기고, 과제가 생겨야 D를 재현할 수 있고, C는 양을 늘리는 일이라 마지막이다.

F에서 실제로 손댄 규모: 비테스트 8개 수정·삭제 + 새 파일 4개, 테스트 9개.
(2026.09.15 이전 기록의 "비테스트 12개 + 테스트 4개"는 잘못 센 숫자였다)

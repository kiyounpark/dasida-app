**R1. 권고: 놓친 과제마다 한 번만 한 칸 내리고, 예정일은 유지한다.**
- day30→day7→day3→day1, day1은 유지. 며칠 늦어도 같은 과제에는 추가 강등하지 않는 안이다. 이는 기윤의 원문에서 아직 정해지지 않은 부분에 대한 제안이다.
- 기준은 **예정일 다음 날 한국 자정**. 로그인 학생은 서버에서 조회·완료 처리 시 반영하고, 게스트는 같은 규칙을 로컬에서 적용한다. 앱 복귀·직접 복습 진입에도 적용해 홈을 거치지 않아도 같아야 한다.
- 날짜를 유지하면 돌아온 날 바로 복습할 수 있다. 현재 앱·서버 모두 `scheduledFor <= today`다(`features/learning/local-learning-history-repository.ts:79`, `functions/src/learning-history.ts:549`).
- 과제에 `overdueAppliedFor` 같은 적용 표식을 저장하고, 예정일과 일치하면 다시 내리지 않는다. day1에도 표식을 남긴다. 다음 복습이나 「틀림」으로 새 일정을 만들면 새 적용 기회가 된다.
- **강등된 과제를 성공하면 낮아진 단계의 다음 단계로 간다.** 예: day7을 놓쳐 day3으로 내려갔다면, 성공 후 다시 day7을 예약한다. 간격은 기존처럼 완료일 기준이다(`features/learning/review-scheduler.ts:76`).
- **강등 때 id는 유지하고, 단계는 `stage`를 기준으로 삼는 안을 권한다.** 다음 과제는 단계 문자열만으로 식별하지 말고, 이전 과제 id에서 결정적으로 파생한 새 회차 id를 사용한다. 완료 재요청은 무시해 중복 생성도 막는다.
- 이유: 단순히 `__day7`을 `__day3`으로 바꾸면 이미 완료한 day3과 충돌한다. 현재 `alreadyExists`는 완료 여부와 무관하게 막는다(`features/learning/review-scheduler.ts:65`).
- 서버는 id 변경 시 이전 문서를 실제로 삭제한다. 따라서 「예전 문서가 무조건 남는다」는 문제는 아니지만, 과거 id 참조와 충돌은 별개다(`functions/src/learning-history.ts:1162`, `:1169`).
- 로그인 과제의 강등·완료는 서버 트랜잭션으로 판정하고 저장해야 한다. 현재 전체 목록 저장은 조회 후 batch여서 오래된 다른 기기의 저장이 새 상태를 덮을 수 있다(`functions/src/learning-history.ts:1159`).
- **main의 repair와 id 기반 다음 단계 계산은 교체 대상**이다. 그대로 두면 의도한 강등을 되돌린다(`features/learning/review-scheduler.ts:53`, `:115`).
- 구버전 데이터에서 id보다 stage가 낮은 미완료 과제는 이미 강등된 것으로 인정하고, 추가 강등 없이 적용 표식을 붙인다. 미래로 밀린 날짜는 이관 당일로 당겨 바로 할 수 있게 하는 안을 권한다.
- 원래 예정일·강등 횟수는 저장 필드만으로 복원할 수 없다. 이미 repair된 데이터나 완료 후 다음 과제가 끊긴 사례까지 정확히 복구 가능한지는 모른다(`features/learning/types.ts:13`; 옛 로직 `0c45017^:features/learning/review-scheduler.ts:98`).

**R2. 다음 날 아침 재알림은 유지하되, 문구는 상태에 맞춘다.**
- 예정일을 유지하므로 현재 아침의 어제까지 조회하는 규칙과 맞는다. 다만 과제별 발송 보장이 아니라 계정별·날짜별·시간대별 중복 억제다(`functions/src/review-reminder-core.ts:21`, `:47`).
- 아침 초안: **“복습할 문제가 있어요. 지금 이어서 해볼까요?”** 오늘 과제와 어제 과제에 모두 맞는다.
- 홈 초안: 오늘 예정인 day3 이상은 **“오늘 놓치면 복습 단계가 한 칸 내려가요”**. 이미 강등된 과제에는 **“놓친 복습, 지금 이어서 해요”**. day1에는 강등 예고를 쓰지 않는다.
- 따라서 「오늘 안 하면 리셋」을 일괄적으로 「한 칸 내려가요」로 치환해서도 안 된다(`features/quiz/components/review-home-card.tsx:69`). 학생 문구는 별도 검수한다.

**R3. 1.0.12에 넣되, 단순 문구 수정으로 취급하지 않는다.**
- 앱: `review-scheduler.ts`, `types.ts`, 홈·복습 진입 훅, `local-learning-history-repository.ts`, `remote-review-task-store.ts`, 홈 카드.
- 서버: 공유 과제 계약·전이 규칙, `learning-history.ts`의 스키마·동등성 비교·조회·저장·완료 경로, `review-reminder-copy.ts`.
- 서버와 로컬의 별도 완료 경로도 수정해야 한다. 이쪽은 현재도 `stage`로 계산하고 단계 id 존재 여부로 막는다(`functions/src/learning-history.ts:861`, `features/learning/local-learning-history-repository.ts:410`).
- 필수 검증: 자정 경계, 장기 미접속·반복 실행, day1 하한, 강등 후 성공·재오답, 완료 id 충돌, 완료 재시도, 구버전 이관, 동시 기기·오프라인 재연결, 다음 날 알림.
- **서버 배포가 필요하다.** 서버 호환 처리를 먼저 준비하고 앱을 출시한다. 구버전 저장이 새 표식·단계를 훼손하지 않도록 버전 구분과 서버 보호가 필요하다. 현재 원격 저장은 전체 목록을 보내고 실패 시 로컬에만 저장한다(`features/learning/remote-review-task-store.ts:69`).
- 출시 판단: 초대 전에 이 규칙과 검증을 마치는 쪽을 권한다. 일정이 부족하면 초대를 미룬다. 한 칸 내림 자체는 반대하지 않지만, 미접속을 기억 실패로 보는 것은 제품 가정이며 실제 학습 효과는 여기서 확인하지 않았다.
- 코드·이전 커밋만 읽었다. 수정·배포·테스트 실행은 하지 않았다.

## 확정 — 코드로 본 것

### 1. 스토어 앱에는 사진 부품이 아예 없다

사진첩을 여는 네이티브 모듈 `expo-image-picker`가 `package.json`에 들어온 커밋은 `d470192` (2026-08-01). 마지막 릴리스 커밋은 `64348b7` (2026-06-05). 두 달 차이라 06.25 제출 빌드가 어느 커밋이든 이 모듈은 못 들어간다.

- **(가)든 (나)든 스토어 유저에게 닿으려면** `npx expo prebuild --clean` → 재빌드 → 심사가 앞에 선다. 코드로 못 넘는 벽이다.
- ⚠️ **지금 `eas update`(JS만 밀어넣기)를 누르면 라이브 앱이 죽는다.** `runtimeVersion.policy: 'appVersion'`(`app.config.js:5`)이고 `version: '1.0.6'`(`:13`)이라 스토어에 깔린 1.0.6이 그대로 받아간다. 막는 게 아무것도 없다. 방어는 버전을 먼저 올리는 것.
- ⚠️ `pickPhoto`는 **사진첩만** 연다(`analyze-photo-request.ts:19-31`, `launchImageLibraryAsync`). 촬영 경로 코드는 0건 — "사진 찍으면"이 아니라 "찍어두고 고르면"이다. 귀찮음 축에서 이 한 탭은 아직 아무 크기 판정에도 안 들어갔다.

### 2. 사진 flow는 저장을 0줄도 안 한다

`features/photo` 전체에 AsyncStorage·Firestore 호출이 0건. 화면에도 그렇게 적혀 있다 — `photo-note-card.tsx` *"📸 아직 저장은 안 돼 — 캡처해서 가져가."*

### 3. "저장만 되면 알림·복습은 공짜"는 반만 참 (08.01 🔒 수정 필요)

**참인 절반 — 진짜 공짜**
- 복습 화면은 **문항 원본이 필요 없다.** 과제에 문항도 지문도 없고, 화면이 쓰는 건 약점 이름 한 줄뿐(`review-session-screen-view.tsx:132`). 내용은 `weaknessId`로 정적 맵에서 꺼내는데 58개가 채워져 있다(`data/review-content-map.ts`).
- 서버 푸시 문구도 공짜 — 약점 이름을 안 넣고 고정 문구를 쓴다(`send-review-reminders.ts:78`).
- → **사진에서 온 노트든 10문제에서 온 노트든 화면은 똑같이 그려진다.**

**거짓인 절반 — (가)에 붙는 추가 비용 넷**
1. **홈 복습 카드와 내 기록에는 안 뜬다.** 그 둘은 복습 저장소를 안 읽고 **별도 요약 사본**을 읽는다(`home-state.ts:298-299`, `history-insights.ts:93`). 그 사본은 `recordAttempt` 안에서만 갱신되고 `saveAll`은 안 건드린다. 사진 flow엔 `recordAttempt`가 요구하는 문항 배열·정답 수·정확도가 없다. **중간~큼.**
2. **알림은 "저장"이 아니라 "서버 저장"에 붙어 있다.** 서버가 Firestore `collectionGroup('reviewTasks')`를 읽는다(`send-review-reminders.ts:50-56`).
3. **푸시 토큰 없는 유저가 많다.** 권한 요청 훅을 부르는 화면이 결과 화면 하나뿐이고(`use-result-screen.ts:120`) 약점이 1개 이상일 때만 켜진다. 사진만 쓴 유저는 권한 창을 한 번도 못 본다. 옮기는 건 **작음**(2~3파일 40줄).
4. **발송 스위치가 코드 밖에 있다.** Firestore `config/notifications`의 `enabled`가 true여야 나간다(`send-review-reminders.ts:31-45`). → 미확정 ③

**정리: (가)는 작업 하나가 아니라 넷이다** — 저장(중간~큼) + scheduledFor 통일(큼) + 요약 노출 경로(중간~큼) + 토큰 등록 위치(작음).

### 4. 예약급 — 지금 안 정하면 마이그레이션이 붙는다

저장 경로를 붙이는 날 **이 일곱 개를 먼저 정하고 시작할 것.**

1. **`scheduledFor` 형식.** 클라가 `'2026-08-14'`(날짜만)를 만드는데(`review-scheduler.ts:12-17`) 서버 스키마는 `z.string().datetime()`(`functions/src/learning-history.ts:254`)이라 zod 4가 거부한다. 날짜를 만드는 함수가 세 곳(`review-scheduler.ts:12-17` · `local-learning-history-repository.ts:45-50` · `current-learner-controller.ts:911-916`)인데 규칙이 둘로 갈려 있고, 읽는 쪽 `.slice(0,10)` 비교가 7곳. **새 개념 1개**: 복습 하루의 경계를 KST 몇 시로 볼 것인가(서버 알림 창은 UTC 자정 기준 — `review-reminder-core.ts:5-13`). ⚠️ zod 4는 `+09:00` 오프셋도 거부한다 — `toISOString()`으로 Z를 찍을 것.
2. **`ReviewTask` 스키마에 필드 추가.** 필수로 추가하면 기존 Firestore 문서 전부가 parse에서 throw하고 화면이 **에러로 죽는다**(비는 게 아니라). **optional로만 추가할 것.** 그리고 `ReviewTask`에는 `schemaVersion`이 없다 — 같은 파일 `LearningAttempt:43`엔 있는데 여기만 빠져서 옛 데이터를 구분할 표식이 없다.
3. **새 약점 id를 만들 것인가** (고3 트리 쪼개기). `WeaknessId` 문자열이 Firestore에 그대로 저장되고 서버 `z.enum`이 **읽기에도** 걸린다(`learning-history.ts:997`). 나중에 옛 id를 빼는 순간 그 학생 기록 조회가 통째로 throw한다. 게다가 목록 사본이 클라(`data/diagnosisMap.ts:73`)·서버(`functions/src/learning-history.ts:54`) 양쪽에 있고 **둘이 같은지 비교하는 테스트가 없다.**
4. **`LearningSource`에 `'photo'`를 넣을지.** 안 넣고 시작하면 사진 오답이 `'weakness-practice'`로 굳어 나중에 출처를 못 가른다. (저장 자체는 안 넣어도 성립 — `review-scheduler.ts:140`)
5. **`sourceId` 규칙.** 과제 id가 `${sourceId}__${weaknessId}__${stage}`라서, 기존 것과 겹치게 잡으면 **기존 day1 과제를 덮어쓰고 나머지 pending을 지운다**(`review-scheduler.ts:120-129`). `PhotoNote`에는 id 필드가 없다.
6. **사진 파일을 어디에 둘 것인가.** `photoUri`는 ImagePicker 캐시 경로다. 그대로 저장하면 경로 문자열만 남고 기기가 바뀌면 빈 칸이다. Storage 업로드는 **비용 축이 새로 열리는** 결정.
7. **(나)안 한정** — 홈을 사진 축으로 바꿀 때 `practiceGraduatedAt`이 이미 찍힌 유저를 어디로 보낼지.

### 6. 고3 트리 숫자 (08.13 브라우저 전수 실측)

| | 칸 수 |
|---|---|
| 전체 (풀이법 31 × 실수유형 6) | 186 |
| 빈손 | **131** |
| 하나로 좁혀짐 | 50 |
| 여럿 | 5 |

`weakness-mistake-type-map.test.ts:105`가 `expect(empty).toBe(131)`로 박아뒀다. 빈손 131 중 **75칸이 고3·심화 15개 풀이법**에서 나온다 — 선택지 3개가 전부 같은 약점 하나를 가리키기 때문.

여럿인 5칸:
```
diff+procedure_miss     → 풀이 순서 혼동 · 미분 활용 오류
radical+calc_slip       → √ 간소화 실수 · 분모 유리화 실수 · 유리화 계산 오류
polynomial+calc_slip    → 전개 부호 실수 · 동류항 정리 실수
proposition+concept_gap → 역·이·대우 혼동 · 필요충분조건 오류 · 전칭·존재 명제 혼동
linear_eq+concept_gap   → 이차부등식 범위 오류 · 정의역·치역 혼동
```

⚠️ **어떤 풀이법도 선택지가 3~5개라 6칸을 산술적으로 못 채운다.** 트리를 다 파도 상한이 안 찬다.
⚠️ 같은 기준(선택지가 전부 한 태그)에 걸리는 건 고3 15개가 아니라 **17개**다(`radical`·`proposition` 추가).
⚠️ `radical+calc_slip`의 후보 3개 중 둘은 같은 뜻이다 — '분모 유리화 실수' vs '유리화 계산 오류'. 원본 58개 목록의 중복이라 저장 붙일 때 병합 판단.

### 7. `analyzePhoto`는 인증 없는 공개 엔드포인트다 — 사진 1장 = 돈

`cors: true, invoker: 'public'`(`functions/src/analyze-photo.ts:48-52`). 본문 검증은 이미지 data URL 형식뿐이고 **App Check도 레이트리밋도 없다**(`functions/src`에 `appCheck|rateLimit` grep 0건). URL은 앱 바이너리에 하드코딩(`analyze-photo-request.ts:6`).

처리량 상한이 이미 박혀 있다: `maxInstances: 3, concurrency: 5`(`:54-55`) = **동시 15**. 서버 60s·클라 75s 타임아웃.

→ 오르비 글 하나가 터지면 16번째 학생부터 *"분석 서버가 500으로 답했어"*(`:99`)를 본다. **(나) 전면 전환은 "모든 유저 × 모든 사진"이라 이 축이 크기 판정에 반드시 들어가야 한다.**

### 8. 개인정보처리방침에 "사진"이 없다 — 심사 벽이 prebuild만이 아니다

`public/privacy/index.html` 수집 항목은 이메일·소셜 UID·Firebase 익명 UID·학습기록뿐. **"사진"·"이미지"·"국외 이전" 단어 0회**이고 OpenAI는 "AI 학습 피드백 생성"으로만 적혀 있다(시행일 2026-04-07).

학생 손글씨 시험지를 미국 서버로 보내는 기능은 **방침 개정 + App Store App Privacy / Play Data safety 신고**가 (가)·(나) 양쪽 앞에 선다.

### 9. web-proto는 죽은 프로토가 아니다 — 세 번째 길

같은 `analyzePhoto`를 부르는 **배포본**이고(`web-proto/app.js:4`) 사진→오답노트 한 바퀴가 거기서 오늘 돈다. 그리고 저장 엔드포인트가 `cors: true, invoker: 'public'` + Firebase ID 토큰 인증이다(`functions/src/save-review-tasks.ts:14-15`, `learning-history-auth` 경유 `:32-39`) — **브라우저에서 부를 수 있다.**

→ 네이티브 재빌드·심사 **없이** "사진 → 저장 → 복습 줄"까지 닿는 경로가 하나 더 있다.

그리고 앱과 웹은 **로직·데이터를 한 벌로 나눠 쓴다** — `web-proto/flow-entry.ts`가 esbuild 번들 통로다(08.13에 통역표·diagnosisMap을 여기로 보냈다). 화면만 두 벌이다.

⚠️ **번들이 낡을 수 있다.** 08.13 재빌드 전까지 웹은 08.02 `7b1b737`(중복 문항 정리)을 11일간 못 받고 있었다. 앱 데이터를 고치면 **번들을 다시 만들어야** 웹이 따라온다.
